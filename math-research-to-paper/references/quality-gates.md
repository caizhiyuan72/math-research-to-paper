# 选题、开写与正式交付条件

正式初稿和正式定稿分别检查。阶段性推导、反例搜索、写作纲要和用户要求的单独审稿可以直接进行。接手已有稿件时先按当前文件恢复证据和问题记录；已有文字可以作为审查材料。任何一次检查未过，先在本轮继续做能修补缺口的工作。若仍未通过，交付已核实的阶段结果，列出具体缺口及复现位置。

## 选题前核查价值与可行性

用户给的是宽泛领域时，从例子、定理假设或证明方法中形成一小组能写出精确陈述的候选。为每个候选记录最近的原始出处（含定理编号及阅读范围）、已知结果能直接推出什么、可能的增量、第一道技术障碍和一个能较快验证的子问题。优先尝试一两个有希望的候选，实际推导一个入口引理、测试最小例子、检查一般理论是否已涵盖，或构造反例，再说明为何选择其中一个、放下其余方向。只有一个给定问题时，直接核验这一个；确有差距时可以比较它的不同切入点。

从 `assets/quality-gates.json` 建立 `quality-gates.json`，在 `scope` 写清候选拟立项的精确问题和范围。在 `topic_checks` 中记录以下三项，各项证据均须对应同一个候选及同一范围。每项包括 `result` 与可定位的 `evidence`。证据只支持继续试探、缺少可能改变判断的关键原文，或新候选只继承了旧候选的试验时，`topic_status` 保留 `exploring`。三项对同一范围都成立后才改为 `selected`。

| 字段 | 通过条件 |
| --- | --- |
| `gap` | 对照最近原始定理的假设、结论和已知推论，写明拟研究的部分为何未被直接覆盖。说明是文献明确提出的问题，还是经有限查找后仍有希望的自拟问题。文献现状不明时保留待核实状态。 |
| `value` | 说清回答这个问题能增加什么数学认识，例如揭示一个结构、定位某假设的必要性，或能解释一类已知现象。同时写清最低有价值的目标与更强的目标，避免把论文的成立寄托在最难猜想上。 |
| `tractability` | 已对选中方向做实质试探并记录结果、范围和最小后续任务。若试探发现现题被覆盖、目标错误或入口不可行，调整范围并重新核查。 |

执行 `python <skill-directory>/scripts/check_release.py topic claims.json quality-gates.json --root .`。选题阶段可使用空台账，研究试探仍可继续。通过表示选中方向有明确依据，原创性判断仍随文献和证明演进。接手用户指定课题、旧证明或已有论文时，可用实际成果补齐已有题目的选题记录，无须重新发散选题。

## 开写前核查研究深度

确认 `scope` 是拟成文的准确范围，在 `core_claims` 列出承载贡献的主张 ID。每项检查都填写 `result` 和 `evidence`。证据写到读者能复核的位置，例如引理编号、代码与日志、正式定义、文献定理及阅读范围。

| 字段 | 通过条件 |
| --- | --- |
| `contribution` | 写出准确的主问题、假设和结论。明确相对最近已有工作的具体增量及数学价值，指出支撑增量的结果，例如结构定理、严格新界、反例、完整分类，或有独立价值的新证明。凭样例形成的猜想、已知定理的直接代入或单纯扩充篇幅，均无法单独支撑研究论文。 |
| `proof` | 主结果及所需内部依赖都已建立。沿每条证明链核对关键方向、量词、边界、调用定理的假设。计算机辅助结论须有完整有限归约、覆盖与去重论证、可运行的验证器或证书。 |
| `stress_test` | 先指出哪些薄弱环节一旦失败会推翻主结果，再对关键薄弱环节换路线检查，例如寻找最小反例、手推退化情形、用独立算法复算，或从原定义验证关键引理。记录所检验的断言、方法、结果和范围。若主要漏洞仍无法排除，该项未通过。 |
| `literature` | 用确切出处与最近的定理逐项对照对象、假设、结论和方法，并记录尚未查清的重叠。若无法判断核心结果是否已被涵盖，把该项留待核实。 |

执行 `python <skill-directory>/scripts/check_release.py draft claims.json quality-gates.json --root .`。任一项缺证据时，写出会改变判断的下一个具体数学任务。若某条路线失败，可推更小的子定理、尝试独立证明或构造反例。已有独立价值的结果可以按实际贡献重新核查，外围问题可保留在讨论中。若收窄会改变用户明确要求解决的目标，原目标按阶段性结果汇报。无须为追求深度硬加推广、页数或实验次数。证明范围或证据实质变化时重做受影响的检查。

## 审稿与验收复核

首轮按下表从正文及其依赖出发审查，把具体问题记录为 `findings`。每条记录含 `id`、`problem`、`status`、`resolution` 和 `verification`。`problem` 写清位置、影响、怎样复现或发现。修复时记录改动与涉及的依赖和章节；`verification` 写出复查人在修订版实际检查了什么、结果如何，随后才把 `status` 改为 `closed`。修正命题范围时同时核查摘要、结论、推论及可复现材料，保留原问题和验证记录。单纯改写、口头解释、承诺以后补证或移动到附录都不能关闭仍影响稿件的问题。

| `review.tracks` 字段 | 验收复核至少检查 |
| --- | --- |
| `proof` | 对照实际正文复核全部主定理及关键依赖，关注量词、边界、最小性、证明的每个方向、外部引理假设以及是否循环。给出确切位置和实查结果。 |
| `computation` | 实际重跑关键程序或核验证书，检查覆盖、剪枝和去重。核对正文与表格中的数字、对象口径和范围是否与日志一致；用可手算的小规模基准或不同算法交叉核对。纯理论稿说明无须计算证据的依据。 |
| `literature` | 查最近的原始出处、定理原文的适用条件和重叠范围，核对引用及创新性措辞。 |
| `manuscript` | 核对标题、摘要、定理、证明和结论的范围一致；验证交叉引用、图表、附录及复现说明，实际编译、渲染并检查最终 PDF。 |

首轮意见和作者修改完成后，请独立审查者或另一个上下文完成验收复核。在有权限的环境中可以使用 subagent，或使用用户给出的独立核验报告。给复核者实际稿件、证据文件和明确任务，先让其自行追证明、找反例和查缺项，再交给他核销清单。记录实查范围和结果，对应 `review.mode` 的 `separate-context` 或 `external`。先前写作者在同一上下文重读只能作为补充自审；只有这种自审时，保留为待独立核验的阶段版本。AI 审查需要说明审查方式。

复核发现的新问题重新编号记录，修订后重查相应证明链、证据与下游文字。循环到当前交付范围内，所有已发现问题都有可核验的关闭证据，四项审查均通过。没有固定轮数。若当前权限、材料或技术条件让问题无法关掉，列出未决项及影响，交付阶段稿或修订记录。

## 绑定到实际交付版本

1. 在 `audit_files` 列入本次验收的工作文件，覆盖 LaTeX、BibTeX、最终 PDF、附录、图表和引用的数据/证书、运行说明、审稿回复及其他会随正式稿交付的材料。台账及其列出的证明、代码、日志文件自动纳入。压缩包在验收之后由已验收文件组装。
2. 复核当前文件和已关闭的问题。运行 `python <skill-directory>/scripts/check_release.py snapshot claims.json quality-gates.json --root .`，把输出填入 `review.snapshot`。`review.initial` 记录首轮审稿与覆盖范围，`review.verifier` 写明实际复核方式，`review.tracks` 逐项填写 `result: "pass"` 与具体 `evidence`。
3. 交付前运行 `python <skill-directory>/scripts/check_release.py final claims.json quality-gates.json --root .`。如果审查范围、问题记录或实际交付内容变化，重核改动及受影响的内容，再记录对应快照。验收结果描述所审版本、覆盖范围和已发现问题的关闭状态。

检查器验证台账、记录和文件指纹；数学论证、审查是否真实以及证据是否充分靠实际核查。不要靠填写通过状态来替代核查。
